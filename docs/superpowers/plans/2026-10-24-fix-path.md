# Fix Path Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A "Fix path" action that orders camera keys, routes the camera through free space with detour keys, balances timing in one undo step, and shows the camera path in the 3D view.

**Architecture:** Pure planning modules under `src/path/` (navigation grid, routing, ordering, detours) built on the Suggest Views occupancy grid and a shared camera-curve helper extracted from the camera track. `src/fix-path-events.ts` orchestrates (grid from cached points, plan, Balance, one track edit, markers). UI: a button + options next to Balance, timeline colours, and a path line in the existing camera pose gizmo.

**Tech Stack:** TypeScript, PlayCanvas, @playcanvas/pcui, i18next, Node test harness (`npm test`).

**Spec:** `docs/superpowers/specs/2026-10-24-fix-path-design.md`

## Global Constraints

- Splat file only; no photos, capture poses or `cameras.json`.
- Editor world y-up. Grid = Suggest Views occupancy: voxel = eyeHeight / 4, opaque splats, ≥ 2 per voxel, `occ.isFree(p)` 1-voxel clearance, levels via `findLevels(occ, HEAD_VOXELS, 8 × (eyeHeight/1.6)²)`.
- Box and eye height: the last values used by Suggest Views in this session, else fresh `candidates.prepare` estimates.
- User keys are never moved in space, re-aimed or deleted. Fix path only changes their order/frames and adds `auto` detour keys. A rerun first removes all `auto` keys. Editing an auto key by hand (move, update pose) clears its `auto` flag.
- First key (lowest frame) stays first. "Keep my order" skips reordering. Loop on → closed tour, last→first segment routed.
- Unreachable keys go to the end of the order; their incoming segment is reported as blocked.
- Walking preferred: walk cells at eye height above a standable surface; fly cells (only with "Allow flying", default on) cost extra per voxel above walking height; cells must be inside the box and near scanned geometry (within 3 m × eyeHeight/1.6 of an occupied voxel, measured in voxels: `ceil(3 / 1.6 × 4) = 8` voxels).
- Detour keys: no linger; target = point ahead on the route (1 × eyeHeight ahead), blending to the next user key's target over the last 2 × eyeHeight of the segment; fov linearly interpolated between neighbouring user keys.
- Curve check samples the real camera curve (same spline, smoothness, loop, final frames) every 0.25 voxel of travel; ignores 2 voxels around user keys; max 4 refinement rounds; segments still colliding are reported as blocked.
- One undo step (`trackEdit`). keysChanged during async work → abort, nothing applied. Other Balance failure → order + detours applied with fallback frame spacing (`fallbackAppendFrames` style) and the Balance message shown.
- Markers (blocked segments, unreachable keys, keys inside geometry) are session UI state, cleared on the next track edit or Fix path run; `auto` is saved with the project.
- 3D path line shown when the existing `camera.showPoses` overlay is on; blocked segments red, auto keys in the auto colour.
- New files < 500 lines; `src/ui/timeline-panel.ts` append-only; pure planning code testable in Node; all strings in 9 locales with real translations; comments describe code, not history.
- Performance: Fix path on ~20 keys in the courtyard well under 5 s; log `path.fix: N keys, M detours in X ms` via `console.debug`.

## Review Focus

1. Fewer than 2 keys, or no visible splats: clear message, no edit, no crash.
2. A user key inside geometry or outside the box: reported as "inside geometry", planning terminates, no endless refinement.
3. Undo after Fix path restores keys exactly (frames, names, lingers, `auto` flags).
4. Fix path run twice in a row: second run removes the first run's auto keys; key count does not grow without bound.
5. Loop toggled after Fix path: markers clear, path line updates; no stale red segments.

### Task 2: Navigation grid and routing

**Files:**
- Create: `src/path/nav-grid.ts`, `src/path/route.ts`
- Test: `test/fix-path.mjs`

**Interfaces:**
- Consumes: `Occupancy`, `Level`, `Vec3Like` (`src/candidates/occupancy.ts`, `levels.ts`), `Box`, `insideBox` (`src/candidates/estimate.ts`).
- Produces:
  - `type NavGrid = { voxel: number, cellOf(p: Vec3Like): Cell | null, nearestFree(p: Vec3Like, maxVoxels: number): Cell | null, centre(c: Cell): Vec3Like, neighbours(c: Cell): { cell: Cell, cost: number }[], lineFree(a: Vec3Like, b: Vec3Like): boolean }` with `type Cell = number` (packed key).
  - `buildNavGrid(occ: Occupancy, levels: Level[], box: Box, eyeHeight: number, allowFlying: boolean): NavGrid` — walk cells = free cells at eye height above level surface cells (y = (iy+1)·voxel + eyeHeight, same as Suggest Views cameras), 4-neighbour horizontal steps with |Δy| ≤ 1 voxel (cost 1, √2 diagonals allowed when both orthogonals free); fly cells (allowFlying only) = free, in box, within 8 voxels of an occupied voxel, 26-neighbourhood, cost = step length × (1 + 0.5 × voxels above the nearest walk height below, capped at 10).
  - `findRoute(grid: NavGrid, from: Vec3Like, to: Vec3Like): { points: Vec3Like[], length: number, fromSnapped: boolean, toSnapped: boolean } | null` — A* with Euclidean heuristic; endpoints snapped with `nearestFree(p, 2)`; null when unreachable or an endpoint can't be snapped.

**Interfaces:**
- Consumes: Task 1 `buildCameraCurve`, `CurvePose`; Task 2 `NavGrid`, `findRoute`.
- Produces:
